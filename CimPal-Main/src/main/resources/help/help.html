CimPal

A desktop workbench for CIM / CGMES semantic models — profiles, constraints and instance data.

CimPal is an open-source Java application developed by gridDigIt to support the implementation of the Common Information Model (CIM) and Common Grid Model Exchange Standard (CGMES) profiles in the power sector. It is licensed under the EUPL-1.2-or-later. It helps CIM implementation by providing tools facilitation the work related to SHACL constraints and identification of changed between different versions of CIM. CimPal is a graphical tool for the people who build and maintain CIM based data exchange standards (such as IEC CGMES or IEC 61970-45x), specifications (ENSTO-E Network Codes profiles) and the datasets exchanged under them. It works on three kinds of artefact and, above all, on the relationships between them:

  • RDFS profile definitions — the machine-readable description of a data exchange profile (which classes, which properties, which multiplicities), as produced by CimSyntaxGen or CIMTool from a UML model.
  • SHACL constraint sets — the executable rules that decide whether a dataset conforms to a profile.
  • RDF instance data datasets — the actual exchanged models: CGMES individual and common grid models (IGM / CGM), reference datasets, boundary datasets or other datasets in various serialisations.

Everything in the application is reachable from three places: the tabs in the main window (interactive, multi-step work), the Tools menu (single-shot batch conversions and exports), and the File menu (namespaces, appearance and the cache of downloaded files). The tabs are grouped into three categories — SHACL Generation, RDF Operations and Dataset Operations — which is also how this page is organised. Every operation writes progress and results to the Output panel at the bottom of the window.

Core purpose

CimPal exists to remove the hand-work from four recurring jobs in CIM standardisation and CIM-based data exchange:

  1. Deriving constraints from a profile. A profile expressed as RDFS is declarative but not executable. CimPal generates the corresponding SHACL shapes graph from it, so the profile and the validation rules cannot drift apart.
  2. Converting and normalising models. RDF/XML, Turtle and JSON-LD in, the same in any other serialisation out — with deterministic, diff-friendly ordering, controlled namespace prefixes and CGMES-compliant (IEC 61970-552) instance data serialisation.
  3. Comparing two versions. Whether two profile releases or two instance datasets, CimPal reports what was added, removed and changed instead of leaving you with a textual diff of two large XML files.
  4. Validating and producing test data. Run SHACL constraint sets over whole folders of models and collect the reports; and generate, multiply and deliberately corrupt instance data in order to test the constraints themselves.
  5. Data visualisation and query. Visualising and browsing datasets and querying them. Query results can be saved as .xlsx.

Typical workflows

Publishing a constraint set for a new profile version

  1. RDFS to SHACL — load the profile RDFS files, select the profiles in the tree, set the shapes namespace and base URI, press Create, save the generated .ttl shapes.
  2. Tools ▸ SHACL Constraints ▸ Validate SHACL shapes — confirm the generated shapes are themselves conformant (or simply leave Validate generated SHACL shapes ticked in step 1).
  3. Dataset Operations ▸ SHACL Validation — with the Validate by manual selection workflow, run the new shapes over a folder of known-good models and check that nothing conformant is rejected.
  4. Tools ▸ SHACL Constraints ▸ Export SHACL constraints information to Excel — produce the human-readable constraint documentation that accompanies the release.

Reviewing what changed between two profile releases

  1. RDF Operations ▸ Comparison — load the two RDFS profile files, choose the matching format, run the comparison and read the difference report.
  2. RDF Operations ▸ Convert — optionally normalise both files to sorted Turtle first, so any remaining textual diff is meaningful.

Checking a received dataset

  1. Dataset Operations ▸ SHACL Validation — validate the model against the applicable constraint set. Use Validate by manual selection when you pick the constraint files yourself, or one of the mapping workflows when a CSV drives which constraints apply to which input.
  2. Dataset Operations ▸ Comparison — compare the dataset against the reference or previous version.
  3. RDF Operations ▸ Visualisation — open the objects the validation report or the comparison named, and look at their remaining properties in context.
  4. Dataset Operations ▸ SPARQL Query — answer any ad-hoc question the reports did not cover.

Producing test data for a constraint set

  1. Dataset Operations ▸ Generate — create an Excel template from the profile, fill it in, convert it to CIMXML.
  2. Dataset Operations ▸ Task Wizard — multiply the base model, regenerate identifiers, or deliberately introduce non-conformities to prove that the constraints catch them.

Using the window

  • Two rows of tabs — the upper row selects one of the three categories of work, the lower row the function within it. Switching category does not disturb the other categories: each remembers which of its functions you last had open, and no tab loses its loaded models or field values when you navigate away.
  • Collapsing either half of the window — both Operations (the tabs) and Output are collapsible panels. Click the title of either one to fold it away and give the whole height to the other: fold Operations to read a long validation log full-window, then click its title again to return to exactly the split you had before. The divider between them can also be dragged as usual.
  • Output panel — the panel at the bottom receives all progress and result messages. The bin icon above it empties the panel; hover it for the Clear Output Window tooltip.
  • Status bar — the progress bar at the very bottom shows the progress of the running operation, whichever tab started it. An indeterminate bar means the operation cannot report a percentage.
  • Help badges — the small ? markers next to fields in the tabs show a detailed tooltip on hover. This page reproduces the same texts.
  • Reset — every tab has a Reset button that clears its fields and loaded models without touching the other tabs.
  • This help window — opened with F1 or Help ▸ Help Contents. It is not modal, so you can keep it open while working. Use the toolbar to navigate, change the text size, or open this page in your system browser for printing.

Main GUI tabs

The main window groups its ten functions into three categories, shown as the upper row of tabs; the functions of the selected category are the lower row. The categories reflect what the function operates on, not what it produces:

  • SHACL Generation — deriving and maintaining constraint sets from RDFS profile definitions.
  • RDF Operations — syntax-level work that applies to any RDF graph, whether it is a profile definition or a dataset: comparing, converting, browsing.
  • Dataset Operations — work specific to instance data: comparing, generating, transforming, querying and validating exchanged models.

The categories are listed below in the order they appear, and the functions within each category likewise.

SHACL Generation

Tab SHACL Generation ▸ RDFS to SHACL

Business logic

The primary function of the application: it turns an RDFS profile definition into an executable SHACL shapes graph. Load one or more profile RDFS files, pick the profiles to process from the tree, decide how associations, inheritance, abstract classes and cross-profile references should be constrained, and CimPal writes a Turtle shapes file per profile. Because the shapes are derived from the profile rather than written by hand, the constraint set cannot drift away from the profile it is supposed to enforce.

The tab also generates the optional companions to a constraint release: a datatype map for later instance-data validation, a separate datatypes-only shapes file, and the class inheritance tree.

Tab SHACL Generation ▸ Constraints Operations

Business logic

The spreadsheet-driven operations on a constraint set, for the cases the automatic RDFS → SHACL derivation cannot cover. Three related routines share the tab, each in its own collapsible section with its own Reset and Run; filling in one does not affect the others, and only one section is open at a time.

  1. Generate SHACL constraints based on Excel template takes an RDFS ontology plus a spreadsheet in which each row defines one constraint, and builds the corresponding SHACL shapes graph — letting domain experts author constraints in a familiar tool.
  2. Modify SHACL .ttl based on Excel input takes a spreadsheet of modifications and applies them to an already-published shapes file, which is how targeted corrections are made to a released constraint set without regenerating it.
  3. Split SHACL Constraints .ttl based on Excel template restructures a constraint set into separate deliverable files according to a spreadsheet plan.

The third routine was previously a separate SHACL Organizer tab.

RDF Operations

Tab RDF Operations ▸ Comparison

Business logic

Compares two RDFS profile definitions — typically two releases of the same profile — and reports the semantic differences: classes and properties added or removed, changed multiplicities, changed datatypes and value types. This answers “what actually changed in this release?” without reading a textual diff of two large RDF files, and works across a namespace change so that a version bump does not appear as a wholesale rewrite.

Choose the one matching your input files: RDFS (augmented) by CimSyntaxGen, RDFS (augmented) by CimSyntaxGen with CIMTool, or Universal method incl. SHACL Shapes — the last also compares SHACL shape graphs.

Outputs

  • A modal Comparison RDFS profiles result window listing the differences, with the two compared file names as column headings.
  • If nothing differs beyond the namespace, the information message “The two models are identical if the CIM namespace would be the same.”
  • An error message if a file has no header and its profile namespace prefix is not declared.

Tab RDF Operations ▸ Convert

Business logic

The general-purpose serialisation and model-surgery workbench. It reads RDF in any supported syntax and writes it out in another, but the reason to use it is usually one of the processing options: merging a set of files into a single union model, correcting RDFS package assignments, extracting or listing the class inheritance tree, or adding OWL declarations. Its sorting and prefix-stripping options produce deterministic output, which is what makes generated artefacts reviewable in a version control diff.

Also the converter for datasets and instance data. This tab sits under RDF Operations because conversion is a syntax-level operation that does not care what the graph means, and it is deliberately the only place in the application that converts. It is therefore the tab to use for CGMES instance data as well as for profile definitions: tick Source type and it applies the CGMES / IEC 61970-552 instance data serialisation rules on output. There is no separate converter under Dataset Operations.

Tab RDF Operations ▸ Visualisation

Business logic

A read-only browser for RDF, for the moment when a comparison report or a validation message names a resource and the next question is simply what that object actually looks like. It loads RDF in any syntax Apache Jena can parse and presents it as a subject → predicate → object tree, with filters on each of the three positions and a full text search across all of them. That tree can be left flat, grouped by rdf:type, or nested by the references between resources, which is what turns a list of several thousand subjects into a structure you can walk. Nothing is written: neither the loaded models nor any file on disk is modified.

Every loaded file becomes its own named graph — and every RDF entry of a loaded ZIP archive likewise, so a complete CGMES dataset delivered as one archive arrives as one graph per profile file. Each graph carries a tick box, so the tree can show all of them together or any subset: the EQ file alone, or EQ and SSH together, without unloading and reloading. With more than one graph ticked the tree gains a named-graph level above the subjects; with a single graph the subjects are shown directly.

Alongside the tree there is a graph view: the same content drawn as a node-link diagram, one node per resource and one arrow per triple whose object is another resource. That is the view for a structural question - which classes specialise which, what a class is related to, where a resource sits in the model - because a hierarchy that takes a dozen tree expansions to trace is one picture here. Filter the predicate to rdfs:subClassOf, for instance, and the diagram is the class hierarchy of the loaded profile.

It answers the questions the other tabs do not. Comparison tells you that a triple changed; this shows you the object it belongs to and its remaining properties. SPARQL Query answers a question you can already formulate; this is for looking around before you can. And because it accepts every Jena syntax, it will open a Turtle constraints file or an N-Quads dump just as readily as a CGMES RDF/XML profile file.

What the graph view shows

The diagram follows the filters and the highlight, so it always shows the same content the tree does. Scope is taken from the narrowest thing highlighted, and from the union of them when several rows are:

HighlightedThe diagram shows
A subject in the tree That resource and its immediate neighbours - the triples where it is the subject, and the triples where it is the object.
Several subjects (Ctrl- or Shift-click) All of them and their immediate neighbours in one diagram, which is how two resources get compared or a connection between them found.
A class folder, in a class or a nested grouping Every subject in that folder and their immediate neighbours — the whole Breaker population at once, for instance.

Node size follows the number of relationships a resource takes part in, so the hubs of the model stand out. Clicking a node reports its full URI on the status line. Node labels are drawn while there are 120 nodes or fewer and predicate labels while there are 120 relationships or fewer; past that they would overlap into noise, and hovering a node shows its name instead.

Navigating references

An object row whose value is another resource — Terminal.ConductingEquipment → loc:_abc — can be followed when any loaded file describes that resource. The disclosure arrow says which is which: an arrow means the reference leads somewhere, no arrow means nothing loaded describes it, so you know before you click.

What a reference reaches is read from the models held in memory, not from the rows the tree happens to be showing. A resource the filters excluded, one that fell past the subject cap, and one belonging to a graph that is not ticked can all still be opened: ticking and filtering decide what the tree lists, not what a reference is allowed to reach. Where several files describe the same resource, opening it shows all of their triples together — the EQ name and type beside the SSH state values — and a triple stated identically by two files is listed once.

Double-clicka reference row with no arrow Reports that nothing loaded describes the resource, and gives its full URI. A single click stays silent, so selecting such a row merely to scope the diagram never nags.
Clickthe disclosure arrow itself Expands or collapses, and nothing more. The arrow is how a followed row is closed again.
Right-clickanywhere in the tree Steps back one hop, closing what that hop opened and restoring what was highlighted before it.
Double right-clickanywhere in the tree Unwinds the whole trace and returns to where it started.

References across profile files. A CGMES export normally declares no xml:base, so every file resolves #_abc against its own location: the same Terminal is …/EQ.xml#_abc in the equipment file and …/SSH.xml#_abc in the steady-state hypothesis file. Matching on the URI alone would therefore never carry a reference from one profile to the next. So a reference is resolved by URI first, and any graph that does not have that URI is then tried on the local name — the _abc part — which is what makes EQ / SSH / TP tracing work. Only graphs lacking the exact URI are matched this way, so a file that does have the resource is never second-guessed, and the status line names the graphs a reference resolved into and says when a local name stood in for a URI. The case to be aware of is two unrelated datasets loaded at once: they share their mRIDs, so their resources would be treated as one.

A double click has two things it can report instead of jumping:

MessageWhat it means
… has no row of its own in the tree The resource is in the models, but the tree does not list it — the filters exclude it, it is past the subject cap, or its graph is not ticked. There is nowhere to jump to, so it is opened under the reference row instead.
… is referenced, but nothing loaded describes it No loaded file states anything about the resource, under its own URI or under its local name. Either the reference is dangling, or the file that describes it has not been loaded; the full URI is given so it can be searched for.

In the two nested groupings a resource’s own row can sit deep inside a structure that has to be built a level at a time, so the search for it is bounded. Where the bound is reached the message says the row could not be located in this grouping; Subject (flat) always finds it.

Outputs

  • The graph tree. Subjects sort alphabetically by their displayed form and expand to their predicates; a predicate with a single value is shown on one line, a repeated predicate becomes a node with one child per value.
  • URIs are shortened using the namespace prefixes declared in the source file. Where no prefix applies and the namespace is long enough to crowd the name off the row — a file:///C:/… namespace is mostly folder path — it is stood in for by loc:, so the row reads loc:_1234-5678 instead of the whole path. A graph with a second such namespace gets loc2:, a third loc3:, so two resources never end up sharing a label; the prefixes are assigned per graph, in order of first appearance. A short namespace with no prefix — urn:uuid:, for instance — is left as the document wrote it, because hiding nine characters behind loc: would only make it anonymous. Only the displayed form changes: Copy value yields the full URI, and the filters match it. Literals are shown quoted, with their language tag or datatype where they have one.
  • Copy value puts the full URI or literal of every highlighted row on the clipboard, one per line, ready to paste into a SPARQL query or into a filter field.
  • The status line reports how many of the loaded triples the filters admitted, across how many subjects and graphs; the line under the diagram reports how many nodes and relationships it drew, and for which scope.

Notes

  • Expand selected opens every highlighted branch and everything below it, stopping after 1000 nodes across all of them so that a large subtree cannot lock up the view; expand the remaining branches individually. Collapse all closes everything. It deliberately stops at reference rows: opening one loads the target’s properties, whose own references would be opened in turn, and a single press would chase them across the whole graph until the budget ran out. Following a reference stays a deliberate click.
  • Each graph is truncated at 5000 subjects, and the last row of a truncated graph says so: clicking that row raises the cap by another 5000 and rescans, exactly as Apply does, so the tree collapses and reopens with more in it. The raised cap holds until Reset. Narrowing the filters remains the quicker route when the resource can be named in one — a tree of tens of thousands of rows is not browsable in any case — but the row is there for the resource that cannot be.
  • Relative URIs are resolved against the document's own declared base where it has one, and otherwise against the location the file was read from.
  • A file that cannot be parsed does not abort the load: the remaining files are loaded, and the reason for each failure is written to the Output window.
  • The diagram is capped at 400 nodes. Past that a node-link view is an unreadable tangle well before it is slow, so the cap is about legibility: narrow the filters, or select a subject to see just its neighbourhood. The line under the diagram says when it has been truncated.
  • The layout is deterministic - the same filter and selection always produce the same arrangement - and it is computed fresh on each redraw, so a node you dragged returns to its computed place the next time the scope changes.
  • The class grouping reads rdf:type from the triples the filters admitted. A predicate filter that excludes rdf:type therefore leaves every subject in the (no rdf:type) folder; narrow a class view with the subject or object filter instead.
  • In the two nested groupings, a resource with more than eight nested children has them grouped into class folders, because forty children in one flat list is not browsable. Fewer than that, or a grouping that would produce a single folder, and the children are listed directly.
  • References form a graph, not a tree. A resource reached from two parents appears under each of them, which is what a reference view should show, and a cycle is broken where it closes, so nothing is ever nested under itself.
  • A resource's own properties are listed directly when it has nothing nested under it, and behind a properties folder when it has, so the structure the grouping exists to show stays legible.

Tab Dataset Operations ▸ SHACL Validation

Business logic

Validates datasets against a SHACL constraint set. The Validation workflow choice selects one of three routes, and the rest of the form enables only the fields that route reads.

  • Validate by mapping file — production-scale validation driven by a mapping file. Instead of choosing constraints and models by hand, a CSV declares which constraint files apply to which inputs; CimPal then executes the whole matrix and produces the reports, summaries and ZIP deliverables in one run.
  • Validate by timestamped mapping — as above, but additionally discovers timestamped input files and organises the reports by timestamp, and can compare each run's totals against the previous run's — which is what turns validation from a one-off check into a trend you can watch across releases.
  • Validate by manual selection — batch validation without a mapping file. Point it at constraint files you pick yourself and at the models root folder, and it validates every model archive it finds against those constraints, reporting conformance for each. This is the regression test for a constraint set: run it over a corpus of known-good and known-bad models and confirm that the good ones pass and the bad ones fail for the expected reason. It is equally the acceptance check for a batch of received datasets.

The manual workflow was previously a separate SHACL tester tab. Its “Parent folder for test models” field is now the tab's own Models / input root folder, shared with the two mapping workflows.

All three workflows load their models through the datatype map and base URI. The map is what gives the literals their datatypes as the RDF/XML is parsed, and a constraint on a numeric range or a boolean value can only fire against a typed literal — parsed untyped, every value is a plain string and such a constraint passes a model it should reject. The manual workflow therefore reads the same two fields as the mapping ones, and they stay enabled for it.

ZIP model archives are read directly from their entries into memory. CimPal does not extract input XML files into temporary local folders. After a timestamp or model has been validated, its data graph can be released while the resolved shapes remain available for the next validation. The ZIP files created in the output folder by mapping validation are intentional deliverables, not extracted input data.

Remote constraints and inputs, and what is remembered — a mapping CSV may name an https:// URL where it would name a local file, and GitHub blob, raw and tree links are accepted as written; the same applies to the owl:imports a constraint file pulls in. Downloaded files are kept in a cache folder, but nothing is reused without being checked: each run starts by discarding what it holds in memory, and every cached file is revalidated against the server before it is used again. An unchanged file costs one request and no download; a file edited upstream is downloaded again. So editing a constraint on GitHub and re-running picks up the edit — there is no need to restart CimPal or press Reset first.

One delay is outside CimPal's control: raw.githubusercontent.com serves its own cached copy of a file for a few minutes after a commit, so a re-run inside that window can still be given the previous content by GitHub. If you suspect a stale file for any other reason, File ▸ Clear cached remote data… empties the cache folders outright.

What the tab does remember between sessions is the paths you picked — mapping CSV, models root, constraints root, output folder, previous comparison CSV and a custom datatype map file — never validation data or results. Every run re-reads its inputs from disk or from the web.

Business logic

Applies a SPARQL-defined transformation to a set of models. Settings

Settings File ▸ Preferences…

Business logic

Holds the settings that would otherwise have to be retyped in every tab. The CIM related tab defines the namespaces of the standard CimPal is working against — get these right once and every generated artefact carries consistent, correct namespace declarations; get them wrong and the output is subtly invalid in a way that is tedious to trace. The Application tab controls appearance and the folders CimPal reopens in. Settings are stored per user and persist between sessions.

Settings File ▸ Clear cached remote data…

Business logic

Empties the two folders in which CimPal keeps files it downloaded from the web: remote SHACL constraint files, including everything they pull in through owl:imports, and remote XML inputs named by a mapping CSV. This is not part of normal use. A validation run already discards whatever it is holding in memory before it starts, and every cached file is revalidated against the server before it is reused, so an upstream edit is picked up on the next run by itself. The menu item exists for the two cases revalidation cannot cover: a cached file that is corrupt or truncated, and a server that serves changed content under an unchanged validator. Emptying the cache costs nothing but the time to download the files again.

Inputs

ControlTypeMeaning
Confirmation dialogaction Reports how many files are currently cached and lists the exact folders that will be emptied, before anything is deleted. Cancel leaves everything in place.

Outputs

  • The cache folders are emptied and the number of deleted files is reported. If a file could not be deleted — typically because another program is holding it open — the message names it, and the rest are still removed.
  • Nothing outside those two folders is touched: local constraint files, models, reports, preferences and remembered locations are all unaffected. The next run downloads what it needs.
Where the files are — both folders sit in CimPal's own per-user data directory, %LOCALAPPDATA%\CimPal on Windows and ~/.cimpal elsewhere: shapes-cache holds downloaded constraint files, remote-xml-cache downloaded XML inputs. The confirmation dialog shows the full paths for the machine you are on. Each cached file is stored next to a small .meta file recording the ETag the server gave it; that is what lets the next run ask “has this changed?” instead of downloading it again.
