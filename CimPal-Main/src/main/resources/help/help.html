CimPal

A desktop workbench for CIM / CGMES semantic models — profiles, constraints and instance data.

CimPal is a graphical tool for the people who build and maintain IEC CIM data exchange standards and the datasets exchanged under them. It works on three kinds of artefact and, above all, on the relationships between them:

  • RDFS profile definitions — the machine-readable description of a data exchange profile (which classes, which properties, which multiplicities), as produced by CimSyntaxGen from a UML model.
  • SHACL constraint sets — the executable rules that decide whether a dataset conforms to a profile.
  • RDF instance data — the actual exchanged models: CGMES individual and common grid models (IGM / CGM), reference data, boundary sets.

Everything in the application is reachable from three places: the tabs in the main window (interactive, multi-step work), the Tools menu (single-shot batch conversions and exports), and File ▸ Preferences (namespaces and appearance). Every operation writes progress and results to the Output & Source Code panel at the bottom of the window.

Core purpose

CimPal exists to remove the hand-work from four recurring jobs in CIM standardisation and CIM-based data exchange:

  1. Deriving constraints from a profile. A profile expressed as RDFS is declarative but not executable. CimPal generates the corresponding SHACL shapes graph from it, so the profile and the validation rules cannot drift apart.
  2. Converting and normalising models. RDF/XML, Turtle and JSON-LD in, the same in any other serialisation out — with deterministic, diff-friendly ordering, controlled namespace prefixes and CGMES-compliant (IEC 61970-552) instance data serialisation.
  3. Comparing two versions. Whether two profile releases or two instance datasets, CimPal reports what was added, removed and changed instead of leaving you with a textual diff of two large XML files.
  4. Validating and producing test data. Run SHACL constraint sets over whole folders of models and collect the reports; and generate, multiply and deliberately corrupt instance data in order to test the constraints themselves.

Typical workflows

Publishing a constraint set for a new profile version

  1. RDFS to SHACL — load the profile RDFS files, select the profiles in the tree, set the shapes namespace and base URI, press Create, save the generated .ttl shapes.
  2. Tools ▸ SHACL Constraints ▸ Validate SHACL shapes — confirm the generated shapes are themselves conformant (or simply leave Validate generated SHACL shapes ticked in step 1).
  3. SHACL tester — run the new shapes over a folder of known-good models and check that nothing conformant is rejected.
  4. Tools ▸ SHACL Constraints ▸ Export SHACL constraints information to Excel — produce the human-readable constraint documentation that accompanies the release.

Reviewing what changed between two profile releases

  1. RDF Comparison — load the two RDFS profile files, choose the matching format, run the comparison and read the difference report.
  2. RDF Convert — optionally normalise both files to sorted Turtle first, so any remaining textual diff is meaningful.

Checking a received dataset

  1. SHACL tester or Validation by Mapping — validate the model against the applicable constraint set; use Validation by Mapping when a CSV drives which constraints apply to which input.
  2. Instance Data Comparison — compare the dataset against the reference or previous version.
  3. SPARQL Query — answer any ad-hoc question the reports did not cover.

Producing test data for a constraint set

  1. Generate Instance data — create an Excel template from the profile, fill it in, convert it to CIMXML.
  2. Task Wizard — multiply the base model, regenerate identifiers, or deliberately introduce non-conformities to prove that the constraints catch them.

Using the window

  • Output & Source Code panel — the collapsible panel at the bottom. The Output window tab receives all progress and result messages; Clear empties it. The Source code tab shows the generated constraint source when Show is toggled on. Drag the divider to resize.
  • Status bar — the progress bar at the very bottom shows the progress of the running operation. An indeterminate bar means the operation cannot report a percentage.
  • Help badges — the small ? markers next to fields in the tabs show a detailed tooltip on hover. This page reproduces the same texts.
  • Reset — every tab has a Reset button that clears its fields and loaded models without touching the other tabs.
  • This help window — opened with F1 or Help ▸ Help Contents. It is not modal, so you can keep it open while working. Use the toolbar to navigate, change the text size, or open this page in your system browser for printing.

Main GUI tabs

The eleven tabs of the main window, in the order they appear.

Tab RDFS to SHACL

Business logic

The primary function of the application: it turns an RDFS profile definition into an executable SHACL shapes graph. Load one or more profile RDFS files, pick the profiles to process from the tree, decide how associations, inheritance, abstract classes and cross-profile references should be constrained, and CimPal writes a Turtle shapes file per profile. Because the shapes are derived from the profile rather than written by hand, the constraint set cannot drift away from the profile it is supposed to enforce.

The tab also generates the optional companions to a constraint release: a datatype map for later instance-data validation, a separate datatypes-only shapes file, and the class inheritance tree.

Tab RDF Comparison

Business logic

Compares two RDFS profile definitions — typically two releases of the same profile — and reports the semantic differences: classes and properties added or removed, changed multiplicities, changed datatypes and value types. This answers “what actually changed in this release?” without reading a textual diff of two large RDF files, and works across a namespace change so that a version bump does not appear as a wholesale rewrite.

Inputs

ControlTypeMeaning
Model Afile, required First RDF model file to compare. Supports RDF/XML (.xml, .rdf), Turtle (.ttl) or ZIP archives containing model files.
Model Bfile, required Second RDF model file to compare against Model A.
Scope / RDFS formatchoice, required The version/format of the RDFS profile describing the models. Choose the one matching your input files: RDFS (augmented) by CimSyntaxGen, RDFS (augmented) by CimSyntaxGen with CIMTool, or Universal method incl. SHACL Shapes — the last also compares SHACL shape graphs.
Same CIM namespacecheckbox Treats both models as using the same CIM base namespace even if their actual namespace URIs differ slightly (for example a different version suffix).
Profile namespacecheckbox + prefix Ignores differences in the profile/ontology namespace URI and normalises comparisons using the specified prefix.

Outputs

  • A modal Comparison RDFS profiles result window listing the differences, with the two compared file names as column headings.
  • If nothing differs beyond the namespace, the information message “The two models are identical if the CIM namespace would be the same.”
  • An error message if a file has no header and its profile namespace prefix is not declared.

Tab Excel to SHACL

Business logic

The spreadsheet route into a constraint set, for the cases the automatic RDFS → SHACL derivation cannot cover. It does two related jobs. Create shapes from Excel takes an RDFS ontology plus a spreadsheet in which each row defines one constraint, and builds the corresponding SHACL shapes graph — letting domain experts author constraints in a familiar tool. Apply changes to an existing Turtle file takes a spreadsheet of modifications and edits an already-published shapes file in place, which is how targeted corrections are made to a released constraint set without regenerating it.

Inputs

The two jobs are two separate sections of the tab, each with its own Reset and Run; filling in one does not affect the other.

Create shapes from Excel — the upper section:

ControlTypeMeaning
RDF filefile, required The RDFS ontology file (.xml, .rdf) containing CIM class and property definitions. Used as the base for generating SHACL shapes from the Excel constraints.
RDFS formatchoice The format/version of the RDFS profile (for example the augmented CimSyntaxGen format).
Input - Excel filefile, required Excel file (.xls/.xlsx) containing SHACL constraint definitions. Each row defines a constraint derived from the RDFS model.
Base URI - Shape graphtext The base URI (IRI) for the generated SHACL shapes graph, used as the graph name in the output.
Prefix / Namespacetext The namespace prefix and URI for the generated shapes graph: the prefix is the short Turtle alias, the URI the full namespace it expands to.

Apply changes to an existing Turtle file — the lower section, headed Modify Constraints from xls file:

ControlTypeMeaning
Changes Excelfile, required Excel file containing constraint modifications to apply to an existing SHACL Turtle file. Each row specifies a change.
Target TTLfile, required The existing SHACL Turtle (.ttl) file to which the changes from the Changes Excel will be applied.

Outputs

  • A SHACL shapes file written to the location chosen in the Save as for shape model dialog.
  • For the changes route, an updated Turtle file saved through a standard save dialog.
  • Progress and any problems reported in the Output window.

Tab RDF Convert

Business logic

The general-purpose serialisation and model-surgery workbench. It reads RDF in any supported syntax and writes it out in another, but the reason to use it is usually one of the processing options: merging a set of files into a single union model, correcting RDFS package assignments, extracting or listing the class inheritance tree, or adding OWL declarations. Its sorting and prefix-stripping options produce deterministic output, which is what makes generated artefacts reviewable in a version control diff. When the source is CGMES instance data it applies the IEC 61970-552 serialisation rules.

Tab Instance Data Comparison

Business logic

Compares two CGMES instance datasets object by object and property by property, so that a regression in a model export, or the effect of a change in a source system, can be identified precisely. It understands the CGMES profile split, so the volatile parts of a model — topology, state variables, diagram layout — can be excluded, and it has a dedicated mode for comparing power flow solutions (State Variables), where matching by ConnectivityNode rather than Terminal is often the only way to align two models. Where a full comparison would be too large to read, it can report instance counts per class instead.

Inputs

ControlTypeMeaning
File Afile, required First CGMES instance data file. Accepts XML profile files or ZIP archives containing several profile XMLs.
File Bfile, required Second CGMES instance data file, compared against File A.
Profile versionchoice CGMES version of the instance data; determines which CIM namespaces are expected in the files.
Base namespacetext The base XML namespace for the instance data. Detected automatically when files are loaded.
Datatype mapchoice / file Datatype mapping used to validate property values during comparison. Select a built-in map or browse for a custom one.
Ignore non-persistent (TP, SV, DL)checkboxes Exclude non-persistent classes: TP topology classes, SV state variables (voltages, flows), DL diagram layout.
SV optionscheckboxes Compare only SV profile restricts the comparison to State Variables data; Rely on ConnectivityNodes uses ConnectivityNodes rather than Terminals for topology matching; Compare only count counts instances per class instead of a full comparison.
Output optionscheckboxes Solution overview gives summary statistics across all profiles; Show details lists per-object differences; Compare Diff shows only the differences; Compare single files compares individual profile files rather than the assembled model.

Outputs

  • A modal Comparison Instance data result window listing per-object differences when Show details is selected.
  • Class-count and solution-overview results written to the Output window.
  • The information message “The two models are identical.” when no difference is found.

Tab SHACL Organizer

Business logic

Restructures a set of SHACL constraint files according to a spreadsheet plan. A generated constraint set arrives grouped the way the generator produced it, which is rarely the way it should be published: constraints need to be split across deliverable files by profile, severity or release. This tab reads the intended arrangement from an Excel sheet and splits the input shapes accordingly, so the packaging of a constraint release is repeatable rather than a manual editing exercise.

Inputs

ControlTypeMeaning
SHACL filesfiles, required Input SHACL shape files (.ttl) to be organised and documented using the Excel template.
Excel templatefile, required Excel template (.xlsx) defining the structure and documentation format for organising the shapes. Produced by the SHACL tester or created manually. The first worksheet is read.

Outputs

  • The reorganised SHACL Turtle files, split as the spreadsheet specifies.
  • Progress in the status bar and messages in the Output window.

Source: SHACLOrganizerController.actionBtnRunShaclOrganizer()

Tab SHACL tester

Business logic

Batch validation. Point it at a constraint set and at a folder tree of models, and it validates every model it finds against those constraints, reporting conformance for each. This is the regression test for a constraint set: run it over a corpus of known-good and known-bad models and confirm that the good ones pass and the bad ones fail for the expected reason. It is equally the acceptance check for a batch of received datasets.

Inputs

ControlTypeMeaning
SHACL filesfiles, required SHACL constraint files (.ttl) used to validate the test models. Several files can be selected and are combined.
Models folderfolder, required Root folder containing the CGMES instance data models to validate. Searched recursively (up to three levels) for .zip model archives.
Export reportscheckbox When checked, saves a SHACL validation report file alongside each tested model in the models folder.

Outputs

  • Per-model conformance results and validation messages streamed to the Output window as the run proceeds, with live progress in the status bar.
  • A validation report file next to each tested model when Export reports is ticked.
  • Nothing happens, and the progress bar resets, if no model archives are found in the folder.

Source: SHACLTesterController.actionBtnRunShaclValidator()

Tab Generate Instance data

Business logic

Creates CGMES instance data from a spreadsheet, in two stages. First it generates an Excel template whose worksheets and columns are derived from the RDFS profile, optionally pre-populated from an existing dataset. Someone then fills that template in — in a tool they already know, with no RDF syntax involved. Second, CimPal converts the filled template into valid CIMXML instance data. This is how small, purpose-built test models and examples get produced without hand-writing RDF/XML.

Inputs

Load instancesfiles, optional CGMES instance data files (XML or ZIP). When loaded, the template is pre-populated with sample values from the instance data.
Hide empty sheetscheckbox Worksheet tabs with no instance data are hidden in the generated template, keeping the file compact.
xls templatefile, required for generation The filled-in Excel template (.xlsx) to convert into CIMXML instance data. It must follow the structure produced by the template section above.
Sorting optionscheckbox + choice Controls output element order: Sort alphabetically sorts subjects by URI, and the secondary strategy sorts by local name or by prefix.
Strip prefixescheckbox Removes namespace prefix declarations not used in the generated XML.

Outputs

  • An Excel template (.xlsx) saved where you choose, with one worksheet per class of the loaded profiles.

Tab Task Wizard

Business logic

A guided, multi-step runner for model manipulation tasks. Each task is a self-contained transformation of instance data, and the wizard walks you through choosing one, supplying its inputs, and running it. Two families of task matter most in practice: scaling — multiplying a base model into a large synthetic system to test performance and assembly — and negative testing — deliberately breaking a valid model (deleting required properties, making datatypes non-conformant) to prove that a constraint set actually detects the defect. The identifier tasks resolve the recurring mismatch between an object's rdf:ID and its mRID.

Inputs

Inputs are per task, collected on the wizard pages that follow the task selection; typically a base instance data model (XML or ZIP), a configuration spreadsheet for the multiplication tasks, and an output location. The twelve available tasks are:

  • Regenerate rdf:ID and mRID — issues fresh identifiers throughout the model.
  • Replaces mRID with rdf:ID — aligns the mRID property with the serialised resource identifier.
  • Delete Required Properties — removes mandatory properties, to test that constraints flag them.
  • Make Non-Conform Datatypes — writes values of the wrong datatype, to test datatype constraints.
  • Rename — bulk-renames objects in the model.
  • Multiply base model N times — replicates the model to build a larger synthetic dataset.
  • Multiply and connect — replicates and electrically interconnects the copies, producing one coherent larger network.
  • Multiply IGM from Config xls — builds individual grid models according to a configuration spreadsheet.
  • Multiply CGM from Config xls — builds common grid models according to a configuration spreadsheet.
  • Change Model Header Description — rewrites the model header description fields.
  • Modify MAS of SV Header — sets the Modelling Authority Set in the State Variables header.
  • Generate Instance Data Model — produces an instance data model from the wizard inputs.

Outputs

  • The transformed or generated instance data files, written to the location the task asks for.
  • Per-task progress and result messages in the Output window.

Source: TaskWizardController.forwardWizardPane(); tasks registered in WizardContext

Tab SPARQL Query

Business logic

The escape hatch for questions no report anticipates. Load any set of models as one combined RDF dataset and run a SPARQL SELECT query over it — to count objects matching a condition, find the instances behind a validation failure, or extract a tabular slice of a model for a colleague. Queries can be saved and reloaded, so a useful investigation becomes a reusable check.

Inputs

ControlTypeMeaning
Select modelsfiles, required One or more RDF/XML files or ZIP archives containing CGMES model data to query. The files are loaded as a combined RDF dataset.
SPARQL querytext, required A SPARQL SELECT query to execute against the loaded model files. Use Load query to import an existing .sparql or .rq file, or type and edit the query directly in the text area.
Save / Save asbuttons Write the current query text back to its file, or to a new .sparql / .rq file.

Outputs

  • A results window presenting the SELECT bindings as a table, with an Export button to write them to a file.
  • Query parse errors and execution messages in the Output window.

Source: SparqlQueryTabController.actionRunQuery(); SparqlResultsWindowController.actionExport()

Tab Validation by Mapping

Business logic

Production-scale validation driven by a mapping file. Instead of choosing constraints and models by hand, a CSV declares which constraint files apply to which inputs; CimPal then executes the whole matrix and produces the reports, summaries and ZIP deliverables in one run. The timestamped workflow additionally discovers timestamped input files and organises the reports by timestamp, and can compare each run's totals against the previous run's — which is what turns validation from a one-off check into a trend you can watch across releases.

Inputs

ControlTypeMeaning
Validation workflowchoice, required Validate by mapping file validates the selected input model structure according to the mapping CSV and creates a validation report and ZIP files. Validate by timestamped mapping discovers timestamped input files and creates timestamp-based validation reports.
Mapping CSV filefile, required CSV mapping file containing the XML input definitions and the SHACL constraint files. Only .csv files are accepted.
Models / input root folderfolder, required For normal mapping, the models root folder. For timestamped mapping, the root folder containing timestamped XML or ZIP files.
Constraints root folderfolder, required Root folder where the SHACL constraint files live. The constraint paths in the mapping file are resolved relative to this folder.
Output folderfolder, required Folder where validation reports, timestamped summaries and generated ZIP files are written.
Datatype mapchoice The CGMES and NC version combination whose datatype map is loaded for validation: CGMES 3.0 / NC 2.5 uses the CIM17 / CGMES 3 / NC 2.5 map, CGMES 3.0 / NC 2.4 the CIM17 / CGMES 3 / NC 2.4 map, CGMES 2.4 / NC 2.2 the CIM16 / CGMES 2.4 / NC 2.2 map.
XML base URItext Base URI used when loading RDF/XML files. The default is normally correct for CIM100 based profiles.

Expected header region,dataset,total where total = warnings + infos + violations — the same shape the comparison workbook emits, so each run's output can feed the next. Left empty, the comparison is produced with an empty previous column.

Outputs

  • Validation report files per input, written into the output folder.
  • ZIP deliverables assembled from the reports.
  • For the timestamped workflow, timestamp-based summaries and a comparison workbook against the previous run's totals.
  • Progress on the tab's own progress bar and messages in the Output window.

Source: ValidationByMappingController.actionRunValidationByMapping()

Tools menu

Single-purpose batch operations. Each one prompts for its inputs with a file or folder chooser, does its work, and reports to the Output window.

The menu is grouped into five submenus by the kind of artefact each tool works on, so a tool can be found by asking “what am I holding?” rather than by scanning one long list:

  • Tools ▸ RDFS Profiles — Export RDFS descriptions; Export RDF tripples to xls; Generate information from RDFS — needed for serialisation; Generate properties info from RDFS (xls, ttl, json); Create datatypes map.
  • Tools ▸ SHACL Constraints — Export SHACL constraints information to Excel; Export All SHACL constraints information to Excel; Validate SHACL shapes; Restore ttl from constraint csv.
  • Tools ▸ Reference Data — Convert Reference Data; Convert Reference data to Common data.
  • Tools ▸ Instance Data & Models — Model transformation; Populate missing attributes; Generate Manifest; PSSE-PowerFactory compare.
  • Tools ▸ Quality Reports — Generate QAR based on xls; Create xlsx template from QAR; QoCDC 3.2.1 xml to Excel.

Two entries stay at the top level of the menu, below the submenus, because they are not batch tools at all: Validate by mapping file and Run SPARQL Query only bring their tab to the front. The cards below are in menu order, submenu by submenu.

Tools ▸ RDFS Profiles

Tool Export RDFS descriptions

Business logic

Extracts the human-readable documentation held in an RDFS profile — the class and property descriptions written by the modellers — into a reviewable form. This is how the narrative part of a profile gets proof-read, translated or published separately from the machine-readable definition.

Preferences

Settings File ▸ Preferences…

Business logic

Holds the settings that would otherwise have to be retyped in every tab. The CIM related tab defines the namespaces of the standard CimPal is working against — get these right once and every generated artefact carries consistent, correct namespace declarations; get them wrong and the output is subtly invalid in a way that is tedious to trace. The Application tab controls appearance and the folders CimPal reopens in. Settings are stored per user and persist between sessions.

Inputs

SettingTabMeaning
CIM namespaceCIM related The base CIM namespace URI used for classes and properties.
CIMS namespaceCIM related The CIM syntax (cims) namespace URI used by the augmented RDFS vocabulary.
RDF namespaceCIM related The RDF namespace URI.
IO prefix / URICIM related Prefix and URI of the namespace declaring IdentifiedObject, used when generating mRID-related constraints.
EU prefix / URICIM related Prefix and URI of the European extension namespace.
Other prefix / URICIM related Prefix and URI of a further custom extension namespace.
Clear remembered locationsApplication ▸ Remembered locations Forgets every remembered field value and dialog folder, after asking for confirmation. The label above the button reports how many are currently remembered. Nothing on disk is touched: path fields simply start empty again and dialogs open in your home folder until you pick a location.
ThemeApplication ▸ Themes One of ten themes, grouped light, dark and accessibility: Minimalist White, Nordic Light, Solarized Light, Sepia (Warm Paper), Sleek Dark Mode, Material Dark, Dracula, Solarized Dark, High-contrast Cyberpunk, High Contrast Black. The selection is applied immediately as a preview — press OK to keep it, Cancel to revert.

Outputs

  • OK — saves the values and closes the dialog. They persist for this user between sessions and are picked up as the defaults by the tabs that offer Apply default namespace and Apply default base URI.
  • Default — restores the shipped default values, and forgets the remembered locations as well.
  • Cancel — discards the changes, including reverting a previewed theme.
Remembered locations — CimPal remembers each path field and each file or folder dialog separately, so a field comes back filled in the next time you start the application and every dialog opens where that same dialog was last used. A field's Reset button also forgets its remembered path. If a remembered folder has since been deleted, the dialog opens in the nearest folder that still exists instead of reporting an error, and a field whose file no longer exists simply starts empty. A few fields show a list of several selected files rather than one path; those cannot be restored into the field, but their dialogs still remember their folder.
Note — a theme change applies to windows that are open at the time and to windows opened afterwards. If this help window is open when you change the theme, close and reopen it from the Help menu to repaint the page in the new palette.
